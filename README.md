# People — a profile board

A Next.js App Router app backed by Supabase. The home page shows member profiles as 3D cards, three at a time, each with the member's name and photo. Members sign in with Google, manage their own name and photo, generate images with AI for open themes, post them, vote on each other's posts, and vote in bracket tournaments between each theme's images.

## Run locally

```sh
npm install
npm run dev
```

Open http://127.0.0.1:3000.

## Supabase

Add your project's credentials to `.env.local` (Project Settings → API Keys in the Supabase dashboard):

```sh
NEXT_PUBLIC_SUPABASE_URL=https://<project-ref>.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=sb_publishable_...
```

Apply the files in `supabase/migrations/` in order, in the dashboard's SQL editor or with `supabase db push`. Without the variables, the board shows only sample tiles.

## Image generation

Images are generated by FLUX.1 [schnell] on Cloudflare Workers AI, which includes 10,000 free neurons a day (roughly 170 images) without a paid plan. Create a free Cloudflare account, copy the account ID from the dashboard, create an API token with the Workers AI template (My Profile → API Tokens), and add both to `.env.local`:

```sh
CLOUDFLARE_ACCOUNT_ID=...
CLOUDFLARE_API_TOKEN=...
```

These are read only on the server (`lib/generate.js`) and never reach the browser.

## Posts and votes

`/create` (signed in only) takes a prompt, generates an image, stores the file in the `generations` storage bucket, and saves a row in `posts` with the prompt and model that made it. The image starts as a draft only its owner can see; Post publishes it and Discard deletes it. Each member can generate 10 images a day.

`/posts` lists every posted image, newest first, and `/people/<id>` shows one member's. Signed-in members can upvote or downvote each image; a vote is a row in `votes`, one per member per post, and clicking the same arrow again removes it. A trigger keeps each post's `score` equal to the sum of its votes.

`supabase/migrations/20261008000000_create_posts_and_votes.sql` creates both tables and their row level security rules: signed-out visitors can only read posted images and profiles; members can create, post and delete only their own images and can never write a score; members can add, change and remove only their own votes and cannot read anyone else's.

## Themes and tournaments

A theme, like "Woodlands" or "Video Game Characters", takes entries for a window of time (24 hours by default) and then becomes a tournament. Each theme is its own row in `themes`, with its own entries and its own bracket, so any number can run at once and changing one never touches another.

When no theme is open, the server asks Gemini for one (`lib/gemini.js`, model `gemini-3.8-flash` unless `GEMINI_MODEL` says otherwise), avoiding the last 30 themes, and opens it with the default window. If Gemini isn't configured or fails, a theme is picked from a built-in list. Opening it needs the project's secret key because visitors can't write themes. Add both to `.env.local` (and to Vercel):

```sh
GEMINI_API_KEY=...            # https://aistudio.google.com/apikey
SUPABASE_SECRET_KEY=sb_secret_...   # Project Settings → API Keys → Secret keys
```

Both are read only on the server. Without the secret key no theme opens automatically, but an admin can still open one.

Each image is tagged with the open theme it was generated for (`posts.theme_id`); when more than one theme is open, `/create` asks which. Row level security only accepts a theme that is open at that moment. When a theme's entries close, its posted images are seeded into a bracket, ordered by their up/down score, with byes for the top seeds when the count isn't a power of two. Members pick one side of each matchup at `/tournaments/<theme id>`; a round lasts 24 hours by default, the side with more votes advances, ties go to the higher seed, and the last image left is the champion. `/tournaments` lists open themes, live brackets and past champions.

The database runs the clock: `public.advance_tournaments()` starts brackets for themes whose entries have closed and closes finished rounds, pg_cron calls it every minute, and pages call it before showing brackets. Matchup votes live in `match_votes` (one per member per matchup, readable only by their owner), and row level security only accepts them while the matchup's round is open. Images made before themes existed have no theme and never enter a bracket.

## Admin panel

`/admin` is for members listed in the `admins` table, which starts with danielitzler@gmail.com. Everyone else gets a 404, and the database checks `public.is_admin()` for every admin action, so the panel can't be used by calling the API directly. Admins can:

- open a new theme at any time, written by hand or suggested by Gemini, now or in a given number of hours, taking entries for as long as they choose; it runs alongside any others
- reword any one theme, change how long it keeps taking entries, close its entries now to start its bracket, or remove one that hasn't opened yet
- end a bracket's current round now, pause and resume it, set how long the round has left, finish it at once, cancel it, or re-seed it from scratch
- decide a single matchup by hand or reopen it, from the admin controls on the bracket page
- change how long new themes take entries and how long rounds last
- delete any post, and see every member with their email and post count

To add another admin, insert their user id in the SQL editor: `insert into public.admins (user_id) select id from auth.users where email = '...';`

`supabase/migrations/20261015000000_create_themes_and_tournaments.sql` and `20261015010000_admin_tournament_controls.sql` add tournaments alongside the existing tables, and `20261015020000_independent_themes.sql` replaces the original one-theme-per-day design with independent themes, carrying every existing theme, image, bracket and vote over. They need the pg_cron extension, which Supabase includes.

## Look and feel

`app/scene.js` runs Conway's Game of Life behind every page and draws each live cell as a small icosphere with Three.js. The board wraps around at its edges and the camera glides over it at an angle, with fog hiding where it repeats, so it looks endless; new patterns are sown whenever fewer than 8% of cells are alive, so it never settles. It sits in the root layout and keeps running across navigations: it follows the pointer (and leaves a faint trail of new cells behind it), takes on each section's accent color (`lib/route-theme.js`), sows fresh life on every navigation, and runs several times faster while a page loads. The floating navigation (`app/nav.js`) also lives in the layout; its highlight glides to the current section and the account link fills in once the session is known.

Page changes animate with React's `<ViewTransition>`: `app/template.js` slides pages left or right depending on which way you move through the nav (other links fade), and `app/loading.js` shows a placeholder the moment a link is clicked, which speeds up the Game of Life and fades out as the page arrives. Page content rises into place in a short stagger (`app/globals.css`). Everything respects the reduced-motion setting.

## The board

`app/page.js` loads members who have finished onboarding, newest first, up to 120. `app/board.js` draws them three at a time with Three.js: each profile is the front face of a box, showing the member's photo (or a blank silhouette) and name. Scrolling down brings up the next row of three (on tall screens, the next card in a column), and only the cards near the view are kept in the scene. Clicking a card brings it forward, dims the others, and opens a panel with more about that member and a link to their posts; Escape, Close, or a click elsewhere puts it back. While fewer than 12 members have joined, sample profiles from `app/placeholders.js` fill the remaining spots.

`supabase/migrations/20261002000000_public_profiles.sql` makes profile rows readable by everyone, signed in or not, so the board can show them. Only a profile's owner can change it.

## Accounts

Visitors sign in with Google at `/login`. Google returns to `/auth/callback`, which starts the session and sends new users to `/onboarding` to enter their first and last name. `/profile` is only reachable when signed in and lets users edit their name and upload a photo.

`supabase/migrations/20261001000000_create_profiles.sql` creates the `profiles` table, a trigger that adds a row for each new user, and a public `avatars` storage bucket. Photos are stored as files in the bucket; the table holds only the file's path.

To enable sign-in, create an OAuth client in Google Cloud with `https://<project-ref>.supabase.co/auth/v1/callback` as an authorized redirect URI, then paste its client ID and secret into Authentication → Sign In / Providers → Google in the Supabase dashboard. Under Authentication → URL Configuration, add `http://127.0.0.1:3000/auth/callback` and `https://<your-domain>/auth/callback` to the redirect URLs.

## Production

```sh
npm run build
npm start
```
